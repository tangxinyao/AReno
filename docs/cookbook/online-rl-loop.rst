Online RL Loop
==============

.. admonition:: Goal

   Understand the key differences between online RL and offline SFT — three new
   stages are introduced: rollout, reward function, and advantage computation.
   Read through the main loop of ``PolicyOnlyTrainer.fit()``.

.. admonition:: Prerequisites

   RL in One Snippet (an overview of RL) and SFT.

.. admonition:: Outcomes

   Understand the main training loop shared by GSPO/GRPO and the four steps:
   rollout → reward → advantage → train.

1 Why Do We Need Rollout?
---------------------------

**Rollout = generating completions with the current policy.** This is the essence
of "online".

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * -
     - SFT (offline)
     - RL (online)
   * - Training data
     - Labeled data prepared in advance
     - Completions **generated by the model itself**
   * - Data updates
     - Unchanged during training
     - After each weight update, the next rollout uses the new policy
   * - Exploration
     - Can only learn answers in the labeled data
     - Can discover solutions **not** present in the training data

Why sample n_samples completions instead of 1?
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Because RL needs **comparison**. GSPO/GRPO group the n_samples completions for the
same prompt together and compare within the group:

- Correct answers → advantage > 0 → encourage
- Wrong answers → advantage < 0 → suppress
- Larger n_samples → more reliable comparison, but rollout time × n_samples

2 How Rollout Changes the Architecture
----------------------------------------

An SFT worker only trains; an RL worker must **alternate between inference and
training**:

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - SFT Worker:
     - RL Worker:
   * - Flow: forward → loss → bwd → step
     - InferenceManager: rollout (forward + sampling), records resp_logprobs,
       continuous-batch scheduling

       TrainingManager: loss_fn computation, backward, optimizer.step()

Engine-level division of labor:

.. list-table::
   :widths: 34 66

   * - ArenoEngine
     -
   * - InferenceManager
     - → manages rollout inference (continuous-batch scheduling)
   * - TrainingManager
     - → manages the optimizer step (loss computation + backward + step)

Inference and training share the same weights — after ``optimizer.step()`` the
changes take effect automatically, with no manual synchronization needed.

3 The Reward Function Contract
--------------------------------

.. code-block:: python

   def reward_fn(record: RewardRecord) -> float:
       """Given a RewardRecord, return a scalar score."""

The key fields of ``RewardRecord`` (source ``areno/api/rewards.py``):

.. list-table::
   :header-rows: 1
   :widths: 24 22 54

   * - Field
     - Type
     - Meaning
   * - ``prompt``
     - ``str``
     - The raw prompt text
   * - ``completion``
     - ``str``
     - The completion text generated by the model
   * - ``answer``
     - ``Any``
     - The ground-truth answer (auto-mapped from the ``solutions`` field)
   * - ``source_record``
     - ``dict``
     - The original data row (you can read any custom field from it)
   * - ``tokens`` / ``logprobs``
     - ``list``
     - The tokens and logprobs from rollout

**Practical tip**: if you use a custom dataset loader, make sure it produces a
``solutions`` field (a list of strings); the trainer maps it to
``record.answer`` automatically.

4 In-Group Advantage Computation
----------------------------------

For the n_samples completions of the same prompt, standardize with an in-group
Z-score:

.. math::

   A_i = \frac{r_i - \text{mean}(r)}{\text{std}(r) + \epsilon}

Source (``areno/api/rewards.py::compute_group_advantages``):

.. code-block:: python

   def compute_group_advantages(rewards: list[float], eps: float = 1e-8) -> list[float]:
       rewards_arr = np.asarray(rewards, dtype=np.float32)
       return ((rewards_arr - rewards_arr.mean()) / (rewards_arr.std() + eps)).tolist()

.. list-table::
   :header-rows: 1
   :widths: 30 14 28 28

   * - Method
     - Needs Critic
     - Pros
     - Cons
   * - In-group standardization (GRPO/GSPO)
     - ✗
     - Simple, no extra parameters
     - Can only compare within the group
   * - Global standardization
     - ✗
     - Simple
     - Inaccurate when different prompts vary in difficulty
   * - GAE (PPO)
     - ✓
     - Accurate, handles sparse rewards
     - Requires training an extra critic

5 A Close Read of the PolicyOnlyTrainer.fit() Main Loop
---------------------------------------------------------

Source: ``areno/api/trainers/policy_only.py::PolicyOnlyTrainer._fit_initialized()``

.. code-block:: python

   for epoch in range(self.config.epochs):
       for prompt_batch in self.areno.load_prompt_batches(dataset, batch_size=..., ...):

           # ─── Step 1: Rollout ───
           rollout_results = asyncio.run(
               self._run_prompt_rollout(sampling_params, prompt_batch)
           )
           # Generate n_samples completions per prompt
           # Each completion = resp_tokens + resp_logprobs

           # ─── Step 2+3: Reward + Advantage + TrainSequence ───
           train_batch, rewards_all, rollout_logprobs = (
               self._materialize_train_batch(tokenizer, prompt_batch, rollout_results)
           )
           # Internally: reward_fn(record) → compute_group_advantages → packed into TrainSequence

           # ─── Step 4: Train ───
           result = self.areno.train(
               train_batch, self.loss_fn,
               mini_bs=self.config.mini_bs,
               gradient_accumulation_steps=...
           )
           # Internally: forward → loss_fn → backward → optimizer.step()

           step += 1

The complete logic of ``_materialize_train_batch``:

.. code-block:: python

   for item, result in zip(prompt_batch.items, rollout_results):
       completions = [tokenizer.decode(seq.resp_tokens) for seq in result.sequences]

       # Score each one
       rewards = [reward_fn(make_reward_record(prompt=item.prompt, completion=c, answer=item.solutions, ...))
                  for c in completions]

       # In-group standardization
       advantages = compute_group_advantages(rewards)

       # Pack into TrainSequence
       for seq, advantage, reward in zip(result.sequences, advantages, rewards):
           train_batch.append(TrainSequence(
               prompt_mask=[1]*prefix_len + [0]*resp_len,
               tokens=item.input_tokens + seq.resp_tokens,
               logprobs=[0.0]*prefix_len + seq.resp_logprobs,  # rollout logprobs → "old logprobs"
               advantages=[0.0]*prefix_len + [advantage]*resp_len,  # advantage broadcast to each response token
               reward=reward, eos_token_id=tokenizer.eos_token_id,
           ))

6 Chapter Summary
-------------------

1. **Online RL = the SFT skeleton + rollout + reward + advantage**
2. **Rollout makes the worker support both inference and training**, and the
   Engine gains InferenceManager
3. **PolicyOnlyTrainer is the Trainer shared by GSPO/GRPO**: a four-step loop —
   rollout → reward → advantage → train
4. **In-group standardization** means policy-only algorithms need no critic
5. **TrainSequence's logprobs come from rollout** (the old policy's logprobs),
   and the advantage is broadcast to every response token

The next three chapters read through the loss functions of GSPO, GRPO, and PPO
respectively — the same four-step loop, but different loss computations.
