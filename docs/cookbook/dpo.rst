1 Core Idea
--------------

**DPO = Direct Preference Optimization**. It takes a completely different path from
online RL:

.. list-table::
   :header-rows: 1
   :widths: 22 39 39

   * -
     - GSPO/GRPO/PPO
     - DPO
   * - Data
     - Completions generated by the model itself
     - Human-annotated preference pairs (chosen vs rejected)
   * - Rollout needed?
     - Yes
     - **No**
   * - Reward function needed?
     - Yes
     - **No** (implicit in the preference data)
   * - Critic needed?
     - PPO needs one
     - **No**
   * - Ref model needed?
     - Optional for PPO
     - **Yes** (required; a frozen reference policy)

Bradley-Terry Preference Model
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Human preference probability is related to the difference in the "implicit rewards"
of the two answers:

.. math::

   p(\text{chosen} \succ \text{rejected}) = \sigma(r_\theta(x, y_w) - r_\theta(x, y_l))

DPO's key insight: there is no need to explicitly train a reward model — express the
reward directly with the policy's log-probability ratio:

.. math::

   r_\theta(x, y) = \beta \cdot \log\frac{\pi_\theta(y|x)}{\pi_{\text{ref}}(y|x)}

Substituting gives the DPO loss:

.. math::

   \mathcal{L}_{\text{DPO}} = -\log\sigma\left(\beta\left(\log\frac{\pi_\theta(y_w)}{\pi_{\text{ref}}(y_w)} - \log\frac{\pi_\theta(y_l)}{\pi_{\text{ref}}(y_l)}\right)\right)

**Intuition**: you want the current policy :math:`\pi_\theta` to increase "chosen
relative to ref" more than "rejected relative to ref".

**The anchoring role of the ref model**: without a ref, the model can lower the loss
by raising the probability of all answers at once. The ref provides a baseline — the
model can only optimize by **relatively** raising chosen.

2 DPO's Special Position in the Architecture
-----------------------------------------------

DPO is offline training, but it still needs a frozen ref model. Training flow:

.. list-table::
   :widths: 40 60

   * - Step / call
     - Description
   * - Dataset (chosen/rejected pairs)
     - Input training data
   * - ``↓``
     - flows into the training flow below
   * - ``DPOTrainer.fit()``
     - training entry point
   * - ``1. ensure_roles({"ref": ModelRole("ref", ckpt, trainable=False)})``
     - register the frozen ref role
   * - ``2. ref.forward(chosen_tokens) → ref_logprobs_chosen``
     - ref logprobs for the chosen sequences
   * - ``ref.forward(rejected_tokens) → ref_logprobs_rejected``
     - ref logprobs for the rejected sequences
   * - ``3. Build the TrainSequence``
     - Pairwise layout: ``[chosen, rejected, chosen, rejected, ...]``

       ``ref_logprobs`` is filled with the ref model's outputs
   * - ``4. trainer.train(batch, dpo_loss_fn)``
     - ``dpo_loss_fn`` recovers the pairs from row order (even rows = chosen, odd rows = rejected)

**Key constraint**: ``--mini-bs`` must be even, so chosen/rejected pairs are never
split apart.

3 Reading dpo_loss_fn in Depth
---------------------------------

Source: ``areno/api/backend/cuda/losses.py::dpo_loss_fn``

.. code-block:: python

   def dpo_loss_fn(data_pack, logprobs, *, beta: float = 0.1, label_smoothing: float = 0.0):
       # 1. Get the response view (needs ref_logprobs and sequence grouping)
       layout = response_layout(data_pack, logprobs,
                                need_ref_logprobs=True, need_sequences=True)

       # 2. The number of sequences must be even
       num_sequences = int(layout.num_sequences) if layout.packed else int(logprobs.shape[0])
       if num_sequences % 2 != 0:
           raise ValueError("DPO requires an even number of sequences per microbatch")

       # 3. Sequence-level logprob sums + the core formula
       ref_logprobs = layout.ref_logprobs.to(dtype=logprobs.dtype)
       return _dpo_from_sequence_logps(
           sequence_sum(logprobs, layout),         # total logprob of each policy sequence
           sequence_sum(ref_logprobs, layout),     # total logprob of each ref sequence
           layout.response_len, float(beta), float(label_smoothing),
       )

Inside _dpo_from_sequence_logps
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: python

   def _dpo_from_sequence_logps(policy, reference, response_lens, beta, label_smoothing):
       import torch
       import torch.nn.functional as F

       # 4. Recover pairs from row order: even rows = chosen, odd rows = rejected
       chosen_policy, rejected_policy = policy[0::2], policy[1::2]
       chosen_ref, rejected_ref = reference[0::2], reference[1::2]

       # 5. The core DPO formula
       logits = beta * ((chosen_policy - rejected_policy) - (chosen_ref - rejected_ref))

       # 6. BCE loss + label smoothing
       losses = -(1.0 - label_smoothing) * F.logsigmoid(logits) \
                - label_smoothing * F.logsigmoid(-logits)
       loss = losses.mean()

       # 7. Diagnostic metrics
       return loss, {
           "dpo_loss": loss.detach(),
           "dpo_accuracy": (logits > 0).to(torch.float32).mean().detach(),
           "dpo_margin": logits.mean().detach(),
           "dpo_reward_margin": (beta * (chosen_policy - chosen_ref)
                                 - beta * (rejected_policy - rejected_ref)).mean().detach(),
           "dpo_chosen_reward": (beta * (chosen_policy - chosen_ref)).mean().detach(),
           "dpo_rejected_reward": (beta * (rejected_policy - rejected_ref)).mean().detach(),
           ...
       }

Line-by-Line Reading
~~~~~~~~~~~~~~~~~~~~~

**Recovering pairs from row order** (Step 4):

.. code-block:: python

   chosen_policy, rejected_policy = policy[0::2], policy[1::2]

Rows 0, 2, 4, ... are chosen and rows 1, 3, 5, ... are rejected. This is the simplest
but most reliable approach — there is no need to explicitly mark pair IDs in the data.

**Core formula** (Step 5):

.. code-block:: python

   logits = beta * ((chosen_policy - rejected_policy) - (chosen_ref - rejected_ref))

- ``(chosen_policy - rejected_policy)``: the advantage of chosen over rejected under the current policy
- ``(chosen_ref - rejected_ref)``: the corresponding advantage under the ref policy
- Subtracting the ref difference → look only at how the policy changed **relative to ref**

**BCE loss + label smoothing** (Step 6): label_smoothing is a form of
regularization — it lets the model be less than fully "confident" in its preference
judgements, preventing overfitting.

**Diagnostic metrics** (Step 7):

.. list-table::
   :header-rows: 1
   :widths: 24 40 36

   * - Metric
     - Meaning
     - Healthy range
   * - ``dpo_accuracy``
     - Proportion of rows where logits > 0
     - >0.5, the higher the better
   * - ``dpo_margin``
     - Mean of logits
     - >0; the larger, the more "confident" the model
   * - ``dpo_reward_margin``
     - chosen reward − rejected reward
     - >0
   * - ``dpo_chosen_reward``
     - The implicit reward of chosen
     - —
   * - ``dpo_rejected_reward``
     - The implicit reward of rejected
     - < chosen_reward

4 Hands-On: DPO Training on Preference Data
----------------------------------------------

Dataset Format
~~~~~~~~~~~~~~

DPO needs preference comparison data. Two formats are supported:

**Format A: Full conversation pairs**

.. code-block:: json

   {"chosen": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "a good answer"}],
    "rejected": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "a bad answer"}]}

**Format B: Shared prompt + different responses**

.. code-block:: json

   {"prompt": "What is the capital of France?",
    "chosen": "The capital of France is Paris.",
    "rejected": "The capital of France is London."}

Dataset Loader
~~~~~~~~~~~~~~

.. code-block:: python

   # examples/dpo/dataset_loader.py
   def load_training_dataset(dataset_path: str, *, default_loader, **_: object) -> list[dict]:
       """Pass through directly; make sure every row has chosen and rejected fields"""
       dataset = default_loader(dataset_path)
       records = []
       for row in dataset:
           record = dict(row)
           if "chosen" not in record or "rejected" not in record:
               raise ValueError("DPO dataset row must contain `chosen` and `rejected`")
           records.append(record)
       return records

Full Training Command
~~~~~~~~~~~~~~~~~~~~~~

.. code-block:: bash

   areno train \
     --algo dpo \
     --ckpt Qwen/Qwen3-0.6B \
     --dataset-path ./my_preference_data.jsonl \
     --dataset-loader-fn examples/dpo/dataset_loader.py \
     --ref-ckpt Qwen/Qwen3-0.6B \
     --dpo-beta 0.1 \
     --tp-size 1 \
     --world-size 1 \
     --batch-size 4 \
     --mini-bs 2 \
     --max-prompt-tokens 256 \
     --max-new-tokens 256

Parameter highlights:

- ``--algo dpo``: select DPO — **no** ``--reward-fn-path`` needed
- ``--ref-ckpt``: the ref reference model. If not specified, it defaults to the same
  checkpoint as the actor (at initialization, actor = ref)
- ``--dpo-beta 0.1``: preference temperature. The larger :math:`\beta` is, the more
  the model "cares" about the preference signal
- ``--mini-bs 2``: **must be even** (2, 4, 8, 16...), so chosen/rejected pairs stay together

6 Chapter Summary
--------------------

1. **DPO is offline preference learning**: no rollout, no reward_fn, no critic
2. **Core formula**: Bradley-Terry preference model → express reward as a logprob ratio → BCE loss
3. **The ref model is key to DPO**: it provides a baseline, preventing the model from raising all output probabilities indiscriminately
4. **Data format**: ``chosen`` / ``rejected`` fields; ``--mini-bs`` must be even
5. **Five-algorithm selection**: SFT as the base → GSPO/GRPO for improvement → DPO for fine-tuning

The next chapter, Agentic RL, enters the world of multi-turn tool use — the model no longer
just "inputs text and outputs text", but completes tasks through multi-turn tool calls.
