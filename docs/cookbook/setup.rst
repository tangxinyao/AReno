What is AReno?
==============

.. note:: TL;DR

   AReno is a single-node, full-stack, self-contained LLM reinforcement learning post-training toolkit. It packs training, inference, and serving into one process so you can run the complete loop — from a base model to a trained Agent — on a single machine. If you are a developer with a programming background who wants to learn LLM reinforcement learning through code, AReno is the best "living textbook" for you.

1 Positioning in One Sentence
---------------------------------

What Is AReno?
~~~~~~~~~~~~~~

**AReno = ASystem Reinforcement Learning Nano**. Broken down:

- **ASystem** — the engineering DNA from Ant Group's ASystem team
- **Reinforcement Learning** — focused on LLM reinforcement learning post-training, not pretraining
- **Nano** — the core idea: nano footprint, full-stack capability

In one sentence: **AReno is a single-node, full-stack, self-contained toolkit for LLM RL post-training.**

But to truly understand what this means, we need to put it in the broader context of the LLM training toolchain.

A Necessary Background: In Online RL, Inference Is Part of the Training Loop
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Before you read on, let's answer the first question you are most likely to have: **"Training is training, inference is inference. They're clearly two sequential stages—so why put them in the same process?"**

This question is entirely reasonable. In most people's mental model, training and inference are two things that **happen in sequence**:

1. **Training**: take a large pile of **fixed** text and update the weights (pretraining and SFT both work this way)
2. **Deployment**: after training finishes, load the weights into an inference service to provide generation

The two steps don't overlap and each uses its own system—there's no reason to merge them. **Traditional training has always been like this, so your intuition is right.**

But one class of training breaks this model — **online RL** (GSPO / GRPO / PPO). Their training data is **not text prepared in advance, but answers "generated by the current model itself."** So "inference" goes from being "deployment after training" to being "a necessary step inside the training loop":

**The loop:**

.. list-table::
   :widths: 30 40 30

   * - ① Rollout (inference)
     - Have the current model generate answers for a batch of prompts
     - ← Here we're doing "inference"
   * - ② Scoring
     - Judge whether each answer is correct / assign rewards
     -
   * - ③ Training
     - Use "answer + score" as training data to update the model weights
     - ← Here we're doing "training"
   * - ④ Back to ①
     - The weights have changed—let the new model generate again
     -

Note that ① and ③ use the **same model, the same copy of weights.** And online RL has a hard requirement: the training signal must come from the **current latest weights** (this is called on-policy). If you train new weights on data generated by an old model, the mismatch between old and new scales distorts the gradients. So every time you step back into ①, you must first hand the latest weights produced by ③ to the generation side.

Hence, two key facts:

1. **The alternation is extremely frequent**: a GRPO training of a few thousand steps is literally thousands of seamless "inference → training → inference" relays;
2. **They share the same weights**: the inference side and the training side must see the same copy of weights, refreshed every round.

That is why "putting training and inference in the same process" is not an arbitrary merge—it solves the real cost that exists in this alternating mode. Just how bad it gets, you'll understand once you read the "traditional three-piece stack" below.

.. admonition:: A Quick Clarification

   This is not the same as "deploying after training ends." After the training loop finishes, if you want to use this model as a service, AReno also offers ``areno serve``—it reuses the same self-built engine, but that is deployment inference in the traditional sense: the process contains only inference, no training. What AReno merges is **inference inside the training loop**, not "training and deployment."

The Traditional Approach to LLM Post-Training: The Three-Piece Stack
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Before AReno existed, doing LLM reinforcement learning training on a single machine usually meant chaining three independent systems together:

.. list-table::
   :widths: 33 33 33

   * - Training framework
     - Inference engine
     - CUDA kernel library
   * - PyTorch FSDP / DeepSpeed
     - vLLM / SGLang
     - Transformer Engine

The problems with this approach are obvious:

1. **Version hell**: the three systems each have their own versions, dependencies, and API conventions. Upgrading one of them can crash the other two
2. **Data transfer overhead**: the training side and inference side are separate processes, and online RL has to switch between them at every step—**each step** must copy the just-updated weights in full over to the inference side and keep two copies, so a few-thousand-step training repeats that a few thousand times
3. **Debugging spirals out of control**: when something goes wrong, you have to jump among the logs, states, and source code of all three systems, making the troubleshooting chain extremely long
4. **Cluster mental burden**: even if you only want to experiment on a single machine, many frameworks force you to write distributed configs

AReno's Approach: One Process Handles Everything
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

AReno's design answers the same question: **if training, inference, and serving are all just different responsibilities of the same process, what would the architecture look like?**

**The AReno single process**

.. list-table::
   :widths: 33 33 33

   * - Trainer
     - Engine
     - accel/
   * - Training loop
     - Inference + training scheduling
     - Self-built CUDA kernels
   * - Zero external backend dependencies
     - Zero inter-process copies
     - Zero distributed config

The core insight here is exactly that necessary background: **the online RL training loop is itself a round-by-round alternation of "inference → training," and it alternates over the same copy of weights.** Instead of bridging two independent systems and shuttling this weight set back and forth across the bridge, why not let training and inference live in the same process—the weights are stored only once, and "the next rollout uses the latest weights" is just an in-process switch. That is what AReno does.

In AReno's own repository words:

   **Small but complete, like its name — nano in footprint, full-stack in capability.**

AReno's Boundaries: Self-Contained on the Policy Side, Bring Your Own on the Task Side
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

How far does "full-stack self-contained" extend? Agentic RL makes this clearest, because it is the easiest place to misunderstand the boundary.

Agentic RL work can be split into two layers:

.. list-table::
   :widths: 30 70

   * - Task / evaluation layer (you provide)—decides what your RL task looks like
     - Environment: spin up a docker sandbox, execute tools, produce multi-turn trajectories
   * -
     - Evaluation: evaluation-set config files, final-result scoring (e.g., Harbor)
   * -
     - Hosting: an agent / evaluation framework that can run the agent function
   * - Policy / training layer (AReno provides)
     - In-process OpenAI-compatible proxy: the agent calls the model through the standard SDK
   * -
     - Records token-level logprobs — the material RL gradients truly need
   * -
     - Explicit trajectories → loss-masked training samples → GSPO / GRPO / PPO

**"Full-stack self-contained" only holds for the lower boundary**: no dependence on external inference engines, training frameworks, or CUDA kernel libraries. **AReno deliberately does not touch the upper boundary**—just as with GRPO's ``reward_fn`` and the data loader being yours to write: the "environment" is inherently part of the RL task, not part of the framework.

So the "evaluation task" in AReno is a set of **function contracts**, not a config file: data is normalized into the row schema of ``{prompt, solutions}`` (``dataset_loader``), scoring is a ``reward_fn(record) -> float``, and agentic adds a ``run_agent(ctx, batch) -> AgentTrajectory`` on top. There is no declarative evaluation-config tree—if you want that kind of structured management, bring your own or plug into a framework like Harbor.

The payoff is free composition: Harbor runs the agent and the evaluation while model calls point at AReno (the in-process proxy during training, ``areno serve`` at deployment), and AReno pulls tokens and logprobs back from OpenAI-compatible responses to feed training. The interface between the two layers is just two things: **OpenAI-compatible calls** + **explicit trajectories**.

Key Design Principles
~~~~~~~~~~~~~~~~~~~~~~~

AReno's design philosophy can be reduced to three principles:

1. **Self-contained**: no dependence on external runtimes such as TransformerEngine, SGLang, or vLLM. CUDA kernels are written in-house, the inference engine is written in-house, and the training loop is written in-house. This means you don't need to worry about problems like "after a training-framework upgrade, the inference engine becomes incompatible."

2. **Single-node first**: AReno doesn't assume you have a cluster. From design day one, it has targeted a single node (one or multiple GPUs, via tensor parallelism) and squeezed single-node performance to the extreme.

3. **Extension by registration, not by fork**: want to add a new algorithm? ``register_algorithm()``. Want to support a new model? ``register_adapter()``. No modifying core code, no forking the repository. This "plugin-style" design makes AReno both a production tool and an experimentation platform.

.. admonition:: Why Nano?

   The name comes from the AReno team's own positioning—they don't chase the fullest feature set or the largest model, but rather "just enough, done to the extreme." Small in footprint (nano), complete in capability (full-stack). As the word Nano itself suggests: it is a system that is maximally compressed yet complete inside.

2 Why AReno Is Worth Learning
---------------------------------

If you are reading this book to "learn LLM reinforcement learning," you might ask: with so many frameworks on the market, why learn with AReno?

Reason 1: Zero External Dependencies — the Code You See Is the Whole Truth
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Most LLM RL frameworks are essentially "glue code"—they stick together PyTorch (training), vLLM/SGLang (inference), and TransformerEngine (CUDA kernels). This creates a fatal problem: **when you want to understand "what actually happens in one RL training step," your reading path has to span the source code of three independent projects.**

Learning RL with AReno has none of this problem. From the ``areno train`` command to the launch of a CUDA kernel, all the code lives in one repository. What you see is everything—there's no black hole like "this calls an external inference engine; for the specific behavior, go read vLLM's docs."

Concretely:

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - Component
     - How other frameworks do it
     - How AReno does it
   * - Training loop
     - PyTorch + DeepSpeed/FSDP
     - Self-built in ``areno/engine/training.py``
   * - Inference engine
     - vLLM / SGLang
     - Self-built in ``areno/engine/inference.py``
   * - CUDA kernels
     - TransformerEngine
     - Self-built in 12 ``.cu`` files under ``areno/accel/csrc/``
   * - Continuous batching
     - vLLM scheduler
     - Self-built ``InferenceManager``
   * - CUDA Graph decoding
     - Depends on the inference engine
     - Self-built in ``areno/engine/runtime/decode_graph.py``

This self-containment is priceless for a learner. When you finish Part 6 of this book (deep architecture), you understand not just "what RL training does," but also "how a high-performance LLM inference engine is written."

Reason 2: An Extremely Minimal Python API — the Core RL Loop Is Under 30 Lines
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

AReno's Python SDK compresses the core RL training loop to the extreme. Take a look first (don't try to understand every detail now—just get a feel for the scale):

.. code-block:: python

   from areno import Trainer
   from areno.api import TrainSequence, gspo_loss_fn

   trainer = Trainer(world_size=1, model_path="Qwen/Qwen3-0.6B")
   trainer.init()

   # RL core loop: rollout → scoring → training → repeat
   async with trainer.rollout_session(sampling_params=sampling):
       sequences = trainer.rollout_token_batch([prompt_tokens], n_samples=8)
   rewards = [reward_fn(seq) for seq in sequences]
   advantages = compute_group_advantages(rewards)
   batch = [TrainSequence(tokens=..., advantages=adv, ...) for ...]
   trainer.train(batch, gspo_loss_fn)

   trainer.close()

**Under 30 lines of code, and it contains the complete data flow of RL training.** This code will be read line by line in RL in One Snippet, with each line leading out to an RL concept. You'll discover that RL's "mystery" actually comes from an opaque toolchain—when the toolchain is compressed into one repository and a few dozen lines of code, RL itself isn't that complicated.

Reason 3: A Progressive Learning Path — from Offline to Online, from Simple to Complete
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

AReno supports five training algorithms, in increasing complexity:

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Algorithm
     - Description
   * - SFT (supervised fine-tuning)
     - ← Simplest, no RL, only next-token prediction
   * - DPO (preference alignment)
     - ← Offline RL, no rollout needed
   * - GSPO (group-sampling policy optimization)
     - ← Entry-level online RL, sequence-level clipping, no critic
   * - GRPO (group-relative policy optimization)
     - ← Token-level fine-grained control
   * - PPO (proximal policy optimization)
     - ← Complete Actor-Critic, with GAE + Critic network

This forms exactly a learning path for RL starting from zero:

- **SFT**: understand "training" itself—how the model gets updated, what loss looks like, what TrainSequence is
- **Online RL Loop, GSPO, GRPO**: introduce rollout and reward functions, understand the core elements that distinguish RL from SFT
- **PPO**: introduce the Critic and GAE, understand the complete Actor-Critic architecture
- **Agentic RL**: extend from single-turn text generation to multi-turn tool invocation

Every chapter builds on the previous one by adding **only one new concept**—you'll never face "you need to understand A, B, and C all at once to read this chapter."

Reason 4: You Learn More Than Just RL
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Because AReno is fully self-contained, by the end of this book you will also understand:

- **How CUDA kernels are written and integrated with PyTorch** (CUDA Acceleration)
- **The engineering implementation of Tensor Parallelism** (Tensor Parallelism)
- **The continuous batching scheduling algorithm** (Inference Subsystem)
- **How CUDA Graph accelerates autoregressive decoding** (Inference Subsystem)
- **How to adapt a new model family to a training framework** (Model Adapters)

This knowledge isn't limited to RL—it is the foundational capability of LLM systems engineering.

3 Relationship with Competitors
-----------------------------------

Inspired by Tinker
~~~~~~~~~~~~~~~~~~~~

AReno's API design is inspired by `Tinker <https://github.com/ThinkingMachine/Tinker>`_ from ThinkingMachines. AReno's README states clearly:

   AReno's API design is inspired by Tinker from ThinkingMachines. We would like to express our gratitude for their pioneering work.

Tinker and AReno share the same philosophy: **the Python API for RL training should be short enough to read on a single screen.** But AReno makes two key advances on top of Tinker:

1. **Full-stack self-containment**: Tinker still relies on an external inference engine; AReno writes even the inference engine itself
2. **Native Agentic RL support**: multi-turn tool-invocation RL training is a first-class citizen in AReno, not bolted on afterward

Organizing Philosophy
~~~~~~~~~~~~~~~~~~~~~~~

The whole book follows one core principle:

   **Every time a new architectural component is introduced, one RL concept is used to explain why it exists; every time a new RL concept is introduced, a piece of code or architecture is used to make it concrete.**

In other words, you won't get a bombardment of RL formulas in the opening chapter, and you won't have to wait long to see your first line of code. **Architecture and concepts advance alternately**—like learning to ride a bike: you don't finish learning physics before getting on; you get on, fall a few times, and later come back to understand why keeping speed keeps you balanced.

Main Thread: Ling-3.0-tiny × AReno
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The whole book runs through one concrete model and one concrete task:

- **Model**: `Ling-3.0-tiny <https://modelscope.cn/models/inclusionAI/Ling-3.0-tiny>`_ (7.9B total params, 1.3B activated, MoE + KDA/MLA hybrid attention)
- **Task**: GSM8K elementary-school math problems → math reasoning RLVR (Reinforcement Learning with Verifiable Rewards)

Reasons for choosing Ling-3.0-tiny:

1. **Moderate parameter scale**: 7.9B runs fully on a single A10 (24 GB) or a DGX Spark (128 GB unified memory)
2. **Architectural diversity**: MoE, KDA, MLA, thinking mode—it covers most of the key designs in modern LLMs
3. **Officially validated by AReno**: peak memory about 8.34 GiB under FP8 (8K context), roughly 100 tok/s on DGX Spark

3 The Call Relationships Between the Six Layers
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A single diagram shows AReno's call hierarchy (top-down):

.. list-table::
   :header-rows: 1
   :widths: 22 50 28

   * - Layer / component
     - Responsibilities / content
     - Calls the layer below
   * - User code / CLI commands
     - ``areno train --algo gspo ...``

       ``trainer = Trainer(...); trainer.train(batch, loss_fn)``
     - ↓ call
   * - Layer 1 · CLI (``areno/cli/``)
     - Parse arguments → build ``TrainerConfig`` → dispatch to algorithm → start the training loop

       ``train.py``: 1700+ lines, the most complex file at this layer
     - ↓ call
   * - Layer 2 · SDK / API (``areno/api/``)
     - ``Trainer.load_prompt_batches()`` → ``rollout_batch()`` → ``train()``

       Algorithm registration: ``register_algorithm(AlgorithmSpec(...))``

       ``Trainer`` subclasses: ``PolicyOnlyTrainer`` / ``PPOTrainer`` / ``SFTTrainer``
     - ↓ call
   * - Layer 3 · Engine (``areno/engine/``)
     - ``ArenoEngine``: launches the Worker cluster, dispatches commands, aggregates results

       ``ArenoWorker``: actually executes forward/backward/``optimizer.step()``

       ``InferenceManager``: continuous batch scheduling → rollout inference

       ``TrainingManager``: ``response_layout`` → loss → backward → step
     - ↓ call (Python)
   * - Layer 4 · Accel (``areno/accel/``)
     - Python Wrapper → PyTorch C++ Extension → CUDA kernel

       ``ops.py``: unified operator interface (upper layers don't see whether the backend is CUDA or PyTorch)
     - ↓ used (via registry)
   * - Layer 5 · Models (``areno/models/``)
     - ``ModelAdapter``: HF config.json → AReno internal network → load weights

       One subdirectory per model family (``qwen3/``, ``llama/``, ``bailing/``, ...)
     - (bottom layer)

Cross-layer communication: Engine ↔ Worker communicate via the RPC protocol defined in ``protocol.py`` (each Worker is an independent process, communicating through ``multiprocessing`` pipes)

6 A General Method for Manually Tracing Call Chains
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

When you need to understand "after a user triggers an action, how is the code passed down layer by layer?", you can use this method:

6.1 Method: grep the keyword → find the definition → trace to the call site → next layer
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Using ``rollout_token_batch`` as an example:

.. code-block:: bash

   # 1. 找到函数定义
   grep -rn "def rollout_token_batch" areno/

   # 2. 看定义处的实现，找到它调了什么
   #    在 trainer.py 中看到调了 self._backend.rollout_batch()

   # 3. 找到 backend 的 rollout_batch 实现
   grep -rn "def rollout_batch" areno/

   # 4. 在 engine/api.py 找到 ArenoEngine.rollout_batch()
   #    看到它构造 RolloutPayload → TPCluster.call(Op.ROLLOUT, ...)

   # 5. 找到 Worker 如何处理 Op.ROLLOUT
   grep -rn "Op.ROLLOUT" areno/engine/worker.py

   # 6. 在 worker.py 找到处理逻辑

**Key trick**: AReno call chains follow a consistent keyword pattern:

- ``CLI`` → ``train_command`` → ``run()`` → ``build_trainer()`` → ``trainer.fit()``
- ``SDK`` → ``Trainer.xxx()`` → ``Backend.xxx()`` → ``Engine.xxx()`` → ``Worker``
- Inside ``Worker`` → ``InferenceManager`` (inference) or ``TrainingManager`` (training)
